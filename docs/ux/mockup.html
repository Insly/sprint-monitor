How the 2-week cycle works

Open on a first visit. Three sprints overlap: one is refined, one is built on Beta, one is tested on Demo and then released to Live.

Bars: outlined grey = build on Beta (10 working days) · blue "Freeze" = code freeze until the Demo update (Tue evening) · light orange "UAT" = clients test on Demo until the fix cut-off · ◆ = refinement sessions, which feed the next sprint's planning · weekends shaded.

Beta → Demo → Live
The three environments. A sprint is built on Beta, moves to Demo on Tuesday evening, and to Live on Monday evening.
Code freeze
From the sprint's last Friday until the Demo update on Tuesday evening. Beta reopens Wednesday.
Demo update / Live update
The 2-weekly deploys. Client project go-lives are not on this board.
Demo/Live matrix
Per-tenant configuration switches. Code always deploys to all tenants.
UAT
Clients test on Demo from Wednesday until the fix cut-off.
Fix cut-off
Monday 12:00 Tallinn time. After it: reverts, not fixes.
Ready for Demo / Ready for Live
Task states set by QA before the Demo update, and by IM / AM after the client signs off.
Release / Golive Release page
Confluence pages "Release 2026-NN" and "Golive Release 2026-NN", written by developers after each update.
Pre-Refinement / Full Refinement
Wednesday 14:00 every week / Thursday 14:00 in week 1. Both estimate work for the next sprint.
Definition of Ready, priority call
What a ticket needs before planning; the call where each client fixes its priorities.
Bug retro
Monday after a sprint ends: review its bugs and escaped defects.
Hotfix
The only change that bypasses the freeze. Event-driven, not on this calendar.
